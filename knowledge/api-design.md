# API 설계·오류 응답·목록 조회

README가 경로·필드·상태 코드·오류 형식을 정했으면 **글자 그대로** 따른다. 아래는 README가 비워 둔 부분을 채울 때의 기본값 — 쓰면 가정으로 기록한다.

## 담당자에게 물을 것 (하나씩)
- "오류 응답은 어떤 모양인가요?" (예: `{"error":"CODE"}`)
- "없는 항목은 404인가요, README의 다른 코드인가요?"
- "목록은 어떤 순서로 정렬하나요? 같은 값이면 다음 기준은?"
- "목록이 많으면 나눠서 주나요? 한 번에 몇 개인가요?"
- "모르는 필드가 들어오면 무시하나요, 오류인가요?"

## 기본값 (README에 없을 때의 흔한 관례)
| 상황 | 상태 코드 |
|---|---|
| 조회 성공 / 생성 성공 | 200 / 201 |
| 입력 형식 오류(필수 누락·타입) | 400 |
| 인증 없음 / 권한 없음 | 401 / 403 |
| 없음 | 404 |
| 상태 충돌(이미 처리됨·중복) | 409 |
| 업무 규칙 위반(재고 부족 등) | 409 또는 422 — 담당자 확인 |
| 서버 오류 | 500 (내부 정보 숨김) |

## 흔한 함정
- 정렬 기준이 하나뿐이라 같은 값끼리 순서가 매번 다름 → **두 번째 기준(ID)** 추가
- JSON이 아닌 본문·빈 본문에서 서버가 죽음 → 파싱 실패는 400
- 숫자 필드에 문자열 `"3"` → 타입 검사 규칙 확정
- 오류에도 성공 때 필드를 섞어 반환 / 성공인데 `error: null`이 빠짐 — 계약대로
- 대소문자·공백 다른 경로(`/items/`) — README 경로 그대로
- CORS·외부 라이브러리 설치에 시간 쓰기 — 같은 출처에서 정적 파일을 서빙하면 불필요
- 검증 순서가 테스트 기대와 다름 → 순서를 문서로 확정

## 구현 요령
- 검증 → 업무 규칙 → 저장 → 응답, 이 순서를 모든 핸들러에서 같게.
- 응답 객체를 만드는 함수 하나(`ok(data)`, `fail(status, code)`).
- 패키지 없이 서버: `recipes/node-server.cjs`, `recipes/python_server.py`.

## 검사 사례
```bash
curl -s -i http://localhost:3000/items                         # 200, 정렬 확인
curl -s -i -X POST -H 'Content-Type: application/json' -d '{}' http://localhost:3000/items      # 400
curl -s -i -X POST -H 'Content-Type: application/json' -d 'not json' http://localhost:3000/items # 400, 서버 살아 있음
curl -s -i http://localhost:3000/items/없는ID                  # 404
```
같은 생성 요청 두 번, 권한 없는 사용자, 큰 본문도 규칙이 있으면 확인.
