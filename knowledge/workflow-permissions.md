# 승인·결재·상태 흐름

핵심은 **상태표 + 권한표 + 오류 확인 순서** 세 가지를 먼저 확정하는 것. 이 셋이 정해지면 코드는 짧다.

## 담당자에게 물을 것 (하나씩)
- "○○ 상태에서 △△를 하면 어떤 상태가 되나요?" (표의 빈칸마다 하나)
- "승인할 수 있는 사람은 누구인가요? 본인 신청을 본인이 승인할 수 있나요?"
- "반려에 사유가 꼭 필요한가요?"
- "승인 뒤에도 취소할 수 있나요? 그때 누가 확인하나요?"
- "오류가 여러 개 겹치면 무엇을 먼저 알려 주나요?"
- "되돌린 수량·잔액은 언제 복원하나요?" (반려 시 / 취소 확정 시)

## 먼저 만들 표
**상태 전이표** — 행: 현재 상태, 열: 동작. 칸: 다음 상태 또는 오류 코드.
| 현재 \ 동작 | 승인 | 반려 | 취소 |
|---|---|---|---|
| 대기 | 승인됨 | 반려됨 | 취소됨 |
| 승인됨 | NOT_PENDING | NOT_PENDING | (담당자 확인) |
| 반려됨·취소됨 | NOT_PENDING | NOT_PENDING | (담당자 확인) |

**권한표** — 동작별로 누가 가능한지(신청자 / 직속 상위자 / 관리자 / 그 외).
**오류 확인 순서** — 예: 없음 → 본인 결재 → 권한 없음 → 상태 → 입력값(사유). 순서가 다르면 같은 입력에 다른 오류가 나서 숨은 검사가 실패한다.

## 흔한 함정
- 표에 없는 전이를 허용(완료 → 대기 같은 역행)
- 권한 검사를 화면에서만
- 상태 바꾸기 전에 다른 값(잔액·재고)을 먼저 바꿔 놓고 오류가 나면 되돌리지 않음 → **검사를 모두 통과한 뒤에** 한 번에 변경
- 공백만 있는 사유를 "있음"으로 처리 (`trim()` 후 판단)
- 오류일 때 응답 형식이 정상과 다름(목록이 빠짐 등) — README의 반환 모양을 오류에도 유지
- 처리자 ID 필드를 기록하지 않음(누가 승인했는지)
- 메모·초안 문서의 규칙을 확정으로 착각 — 담당자 답·README가 우선

## 구현 요령
```js
const NEXT = { pending: { approve: 'approved', reject: 'rejected', cancel: 'cancelled' } };
function act(state, req, action, user) {
  if (!req) return err('NOT_FOUND');
  // 1) 검사만 (상태 변경 없음) — 순서는 담당자 답대로
  // 2) 모두 통과하면 한 번에 변경 + 이력 한 줄 추가
}
```
- 동작마다 `{ ok, error, state }` 같은 같은 모양을 반환.
- 이력(누가·언제·무엇·결과)을 배열로 남기면 감사·디버깅·선택 기능에 다 쓰인다.

## 검사 사례
- 표의 **모든 칸**을 한 줄씩: 대기 → 승인 ✓, 승인 → 승인 → NOT_PENDING …
- 본인 결재 / 권한 없는 사람 / 없는 ID — 오류가 겹치는 입력으로 **우선순위** 확인 (예: 없는 ID를 권한 없는 사람이 → 둘 중 무엇?)
- 반려 사유 `""`, `"   "` → 거절
- 오류 뒤 잔액·상태가 그대로인지
