# 서비스 구조 — 책임 분리·동시 수정·실패·운영 전 점검

로그인·역할·재계산·게시가 있는 웹 서비스 과제용. 확인 문제(데이터 흐름·권한·실패·동시 수정·모놀리스·동기/비동기·운영 전·10배)를 코드 없이 답할 수 있게 이 틀로 만든다. README·담당자 답이 우선. **필요할 때만** 가장 단순한 방법을 쓴다 — 읽기 위주 API에 무거운 쓰기 보호는 과설계다.

## 담당자에게 물을 것 (파일에 없을 때만, 하나씩)
- "두 운영자가 같은 자료를 동시에 고치면 나중 것이 이기나요, 거절하나요?"
- "가져오기 파일 일부가 틀리면 전부 거절인가요, 맞는 줄만 반영인가요?"
- "재계산 결과는 바로 공개하나요, 운영자가 확정해야 하나요? 되돌리기도 필요한가요?"
- "계산은 몇 초까지 기다려도 되나요? 자료는 몇 건까지 늘 수 있나요?"
- "누가·언제·무엇을 바꿨는지 기록이 필요한가요?"

## 흔한 함정
| 함정 | 막는 법 |
|---|---|
| 핸들러 하나에 검증·계산·저장이 섞임 | 아래 5계층, 계산은 순수 함수 |
| 가져오기 중간 실패로 반쯤 바뀐 자료 | 전부 검증한 뒤 한 번에 교체 |
| 재계산 중 이용자가 반쯤 된 결과를 봄 | 조회는 확정본만 |
| 오래된 계산 응답이 새 결과를 덮음 | 입력 버전이 같을 때만 반영 |
| 이용자 화면에서 버튼만 숨김 | 서버도 역할 검사(`security.md`) |
| 메모리 저장인데 "재시작 후 보존"이라 씀 | 실제로 재시작해 확인 |

## 구현 요령

### 1. 책임 분리 5계층
| 계층 | 하는 일 | 규칙 |
|---|---|---|
| 입력 반영 | 업로드·폼 검증 후 저장 | 실패 시 확정본 유지 |
| 계산 | 입력 → 결과 | DB·HTTP 모르는 순수 함수 |
| 확정·게시 | 초안 → 확정, 버전, 되돌리기 | 운영자만. README에 있을 때만 |
| 조회 | 확정본 읽기 | 읽기 전용, 본인 것만, 역할별 필드만 |
| 권한 | 로그인·역할·본인 검사 | 모든 경로가 한 함수를 지남 |

오류 상태(격리 행·실패 작업)는 서비스가 원문·사유와 함께 기록한다. 원자료 정정은 데이터 소유자가, 확정 결과 변경은 업무 결정권자가 승인한다(`data-quality.md` "소유권과 오류 대응").

기존 구조를 먼저 따른다. 새 프로젝트라면 역할 경계가 설명될 만큼만 나누고, 기존 앱 수정이라면 1~2개 파일만 고치는 것이 더 정확할 수 있다. 파일 수나 첫 줄 역할 주석을 강제하지 않는다.
```
server.py    # 경로: 요청 → 권한 → 아래 함수 → 응답
auth.py      # 권한: 비밀번호·세션·역할·본인 검사 (recipes/python_auth.py)
importer.py  # 입력 반영: 전부 검증한 뒤 한 번에 교체
planner.py   # 계산: 순수 함수, DB·HTTP 모름
publish.py   # 확정·게시: 초안→확정, 버전, 되돌리기 (필요할 때만)
store.py     # 저장: SQLite 연결·트랜잭션·version
```
서술형: "운영자 입력은 importer가 검증해 저장하고, planner가 계산한 초안을 운영자가 확정하면 publish가 버전을 올린다. 이용자는 확정본 중 본인 것만 읽는다. 상태는 SQLite 파일 하나, 바꾸는 주체는 운영자 API뿐이다."

### 2. 모놀리스·동기/비동기
| 판단 | 언제 | 가장 단순한 방법 |
|---|---|---|
| 단일 서버 | 기본 | 프로세스 하나 + SQLite 파일 하나 |
| 분리 | 계산이 요청을 오래 막음·부하 편중 | 계산부터 작업 큐로 뗀다 |
| 동기 | 계산 1~2초 이내 | 요청 안에서 계산하고 바로 응답 |
| 비동기 | 수 초 이상 | `POST` → 202 + `jobId`, `GET /jobs/{id}` → `queued/running/done/failed` |

비동기 규칙: 진행 중이면 409 또는 기존 `jobId`. 끝날 때 입력 버전이 시작 때와 같을 때만 반영. 입력이 바뀌면 결과에 `stale: true`. 실패면 `failed` + 확정본 유지. `threading.Thread` + 잠금 dict면 충분하다.
서술형: "작은 규모라 단일 서버로 했다. 계산을 순수 함수로 떼어 두어 느려지면 작업 큐로 옮기면 된다."

### 3. 동시 수정·실패·재시작·멱등·기록
| 항목 | 언제 | 가장 단순한 방법 | 서술형 한 줄 |
|---|---|---|---|
| 동시 수정 | 운영자 여럿이 같은 자료 수정 | `… WHERE id=? AND version=?` 0행이면 409 | "나중 저장이 앞 수정을 덮지 않고 409로 알린다." |
| 트랜잭션 | 한 동작이 여러 행을 바꿈 | `with conn:` 한 블록 | "중간 오류면 전부 롤백된다." |
| 확정본 유지 | 가져오기·재계산 | 다 끝낸 뒤 교체. JSON은 임시 파일 → `os.replace` | "실패해도 이전 확정본이 남는다." |
| 재시작 보존 | README에 저장이 있음 | SQLite 파일, 경로는 `DATA_DIR` | "재시작해도 남는다(실제 확인)." |
| 멱등 | 생성·제출·확정 | 요청 ID 표 또는 상태 검사 | "두 번 와도 한 번만 반영된다." |
| 변경 기록 | README·담당자 요구 | `audit` 표에 같은 트랜잭션으로 한 줄 | "누가·언제·무엇을 남긴다." |
| 자료 오류 | 원자료·가져오기가 틀림 | 감지 → 차단·격리 → 알림 → 정정 승인 → 재처리 → 확인 | "틀린 행은 원문·사유로 격리하고, 소유자가 정정·승인한 뒤 다시 처리한다. 그동안 확정본은 그대로다." |

```python
def update_plan(conn, pid, version, body, actor):
    with conn:                                   # 실패하면 전부 롤백
        cur = conn.execute("UPDATE plans SET body=?, version=version+1 WHERE id=? AND version=?", (body, pid, version))
        if cur.rowcount == 0:                    # 0행: id가 없으면 404, 있으면 아래 409
            return 409, {"error": "CONFLICT"}    # 다른 사람이 먼저 바꿨다 → 새로고침
        conn.execute("INSERT INTO audit VALUES (datetime('now'), ?, 'update', ?)", (actor, pid))
    return 200, {"version": version + 1}
```

### 4. 화면 상태·역할별 화면
- 빈(다음 행동 안내) · 로딩(버튼 비활성) · 입력 오류(칸 옆 이유, 값 유지) · 서버 오류(다음 행동, 409면 새로고침) · 성공(바뀐 것·버전).
- 화면 위에 현재 사용자·역할 표시. 이용자 화면에는 쓰기 버튼을 두지 않고 **서버도 403**.

### 5. 운영 전 체크리스트
"지금 한 것"에는 실제로 한 것만. 안 한 것은 "운영 전에 할 것"으로 말한다.
| 항목 | 지금 한 것(예) | 운영 전에 할 것 |
|---|---|---|
| 비밀값 | 환경변수, `.env` 미커밋 | 비밀 관리 서비스·교체 절차 |
| 로그 | 서버 오류 로그 | 요청 ID·개인정보 마스킹 |
| 헬스체크 | `GET /health` | DB 연결 포함 |
| 백업 | SQLite 파일 하나 | 주기 백업·복구 연습 |
| 권한 | 역할·본인 검사 테스트 | 전 경로 재점검·로그인 잠금 |
| 부하·10배 | "미측정" | 병목 측정: 계산·DB·메모리 |
| 모니터링 | 없음 | 오류율·응답 시간 경보 |
| 롤백 | git 커밋·확정본 버전 | 배포·DB 되돌리기 절차 |
| HTTPS | 없음(시험 http) | 프록시 TLS, 쿠키 `Secure` |

10배 서술형: "먼저 계산·DB·메모리 중 병목을 재고, 계산은 작업으로 돌려 바뀐 부분만, 조회는 색인·페이지, 저장은 PostgreSQL로 옮긴다."

## 검사 사례
- 재시작 보존: 생성 → 서버 종료·재시작 → 그대로 조회
- 동시 수정: 같은 `version`으로 두 번 저장 → 200, 409, 값은 첫 번째
- 실패한 가져오기: 틀린 줄 섞인 파일 → 400, 조회 결과 이전 그대로
- 본인만: 이용자 A 토큰으로 B 자료 → 403/404, A 목록에 B 없음
- 멱등(요청 ID를 쓸 때만):

| 입력 | 기대 |
|---|---|
| 같은 요청 ID + 같은 본문 두 번 | 1건, 두 번째도 **같은 응답** |
| 같은 요청 ID + 다른 본문 | 409, 상태 그대로 |
| 커밋 직전 실패 주입 | 모든 표 0행 → 같은 ID로 재시도하면 1행 |
| 다른 요청 ID + 같은 내용 | 2행(과하게 중복 제거하지 않는다 — 담당자가 막으라 할 때만) |

- 진짜 동시 요청(한정 수량·중복 생성이 요구일 때): 순서대로 두 번은 동시성 검사가 아니다. `threading.Barrier(n)`로 n개를 동시에 출발시킨다. 기대: 생성 1건 + 409 수 > 0(0이면 경쟁이 안 일어났다 → n을 늘려 다시).
```python
import threading, urllib.request, urllib.error, json
N = 8; bar = threading.Barrier(N); codes = []
def hit():
    req = urllib.request.Request(URL, json.dumps(BODY).encode(), {"content-type": "application/json"})
    bar.wait()                                   # 다 모이면 동시에 출발
    try: codes.append(urllib.request.urlopen(req, timeout=5).status)
    except urllib.error.HTTPError as e: codes.append(e.code)
ts = [threading.Thread(target=hit) for _ in range(N)]; [t.start() for t in ts]; [t.join() for t in ts]
assert codes.count(201) == 1 and codes.count(409) > 0, codes
```
- 관측성(운영·장애 질문 대비): 요청마다 JSON 한 줄 로그 `{req_id, method, path, status, ms, error}`(본문·토큰·개인정보 없음) + 응답 헤더 `X-Request-Id`. 진단은 입력 → 단계별 출력을 따라가 **처음 어긋나는 단계**를 찾는다.
- 작업 상태: `queued → running → done`, 틀린 입력 → `failed` + 확정본 유지, 진행 중 재요청 → 409 또는 같은 `jobId`
