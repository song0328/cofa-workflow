# Answers

> 틀 사용법(이 `>` 줄들은 제출 전에 모두 지운다): ⑥에서 제출 루트에 `Answers.md`로 만든다. `playbooks/followup-prep.md` 「Answers.md」대로.
> 제출 문서다 — 확인 문제 출제 AI가 이 파일도 읽는다. 코드·검사 출력으로 확인한 사실만 쓴다. 과장 단정어(최적·항상·보장) 금지.
> 분량·말투·구성은 `templates/Answers-example.md`(가상 예시)를 따른다. 그 문장·숫자는 가져다 쓰지 않는다.
> 답은 쉬운 말로 4~8문장. 근거 줄은 따로 두지 않는다. 숫자는 직접 확인한 것만, 파일·함수 이름은 꼭 필요할 때 한두 개만.
> 사람이 전부 읽고 자기 말로 고친다. 설명할 수 없는 문장과 해당 없는 질문은 지운다. 괄호 안내는 답으로 바꾼다.
> 9번 이후는 `predict_questions.py` 출력의 내 과제 고유 질문에서 고른다. 키트·도구 이름은 이 파일에 남기지 않는다.

## 한눈에
- 만든 것:
- 흐름: (역할) 입력 → 검사 → 계산 → 저장(어디, 누가 바꿈) → (다음 역할) 화면
- 핵심 결정(가장 많이 물을 것):
- 기술·만든 순서: (도구) 자료 읽기 → 계산 → 저장 → 서버 → 화면 → 검사 · 실행 명령 한 줄
- 직접 확인한 숫자:
- 가장 큰 한계 / 운영한다면 먼저 할 일:

## 핵심 결정 집중 — 같은 주제를 여러 번 물어도 각도마다 다른 답
| 각도 | 답 (2~4문장) |
|---|---|
| 왜 이렇게 했나 | |
| 버린 대안과 차이 | |
| 이 결정이 틀리는 입력·약점 | |
| 무엇으로 확인했나 | |
| 조건이 바뀌거나 자료가 10배면 | |
| AI 첫 제안과 내가 바꾼 것 | |

## 1. 핵심 로직은 무엇을 하고, 왜 그렇게 했나?
(입력 한 건이 단계마다 어떻게 바뀌는지 → 왜 이 순서인지 → 약점)

## 2. 데이터는 어디를 거쳐 누구 화면에 보이나? 상태는 어디에 있고 누가 바꾸나?
(누가 넣고 → 어디서 검사하고 → 어디에 저장되고 → 누가 보는지)

## 3. 실제로 구현·검증한 것과 가정으로 둔 것은?
(검증한 것 / 가정한 것 / 확인 못 한 것)

## 4. 서비스 장애는 어디서 가장 먼저 날 것 같고, 나면 지금은 어떻게 되나?
(장애 지점 2~3곳: 증상 → 지금 막은 것 → 운영 전에 할 것)

## 5. 자료가 틀리면 누가 발견하고, 고치고, 승인하고, 어떻게 되돌리나?
(발견 → 격리 → 정정 → 승인 → 다시 처리, 그동안 사용자가 보는 것)

## 6. 트레이드오프와 조건이 바뀔 때 다시 확인할 것은?
(얻은 것과 잃은 것을 숫자로 → 조건이 바뀌면 고칠 곳과 다시 돌릴 검사)

## 7. AI 제안을 그대로 받지 않고 다시 생각하게 한 사례는?
(AI 첫 제안 → 내가 이상하다고 본 점 → 다시 비교한 것 → 최종 결정 → 결과)

## 8. 어떤 기술로, 어떤 순서로 만들었나?
(단계마다 도구 → 하는 일 → 왜. 쓰지 않은 도구는 적지 않는다)
