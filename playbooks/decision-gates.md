# 결정 지점 — 여기서는 AI가 멈추고 사용자가 고른다

AI는 아래 지점에서 **혼자 정하지 않는다.** 선택지 2~3개를 장단점 한 줄씩과 함께 내고, 추천 하나를 표시한 뒤 사용자의 답을 기다린다. 사용자의 결정은 `AGENTS.md`의 확정 사양 또는 가정에 출처("사용자 결정")와 함께 적는다.

| 지점 | AI가 내놓을 것 |
|---|---|
| 과제 유형 판별 직후 | 주 유형과 그 근거, 다르게 볼 여지 |
| 담당자 질문 목록 | 질문 후보(우선순위순). 사용자가 보낼 것을 고른다 |
| 담당자 답이 README·자료와 다를 때 | 충돌 내용, 따를 수 있는 쪽 2개, 추가 질문 한 문장 |
| 구현 계획 | 단계 3~6개. 더 단순한 대안이 있으면 함께 |
| 설계 선택(저장 방식, 구조, 라이브러리) | 가장 단순한 안 vs 대안, 요구에 필요한 이유 |
| README·자료에 업무 기준이 없을 때(아직 담당자에게 안 물음) | **결정 지점이 아니다 — 사용자에게 A/B나 "물어볼까요?"를 묻지 않는다.** 바로 `받는 사람에게: "질문 한 문장?"`을 적어 주고, 그 답에 따라 무엇이 바뀌는지 한 줄. 답을 기다리는 동안 그 기준과 무관한 일만 한다 |
| README가 가리킨 SaaS·공지와 담당자 답이 다를 때 | **결정 지점이 아니다.** 담당자가 그 항목에 기준 없음·공지 따르라고 하면 최신 공지를 채택, 다른 점은 결정 문서에. 담당자가 공지를 보고도 다른 기준을 **명시적으로 확정**했을 때만 결정권자 질문 한 문장 |
| 담당자가 "정해 드릴 기준이 없다"고 했을 때 · 답을 안 줄 때 | 가정안 A/B(각 영향 한 줄 · 추천 표시). **AI가 혼자 고르고 구현하지 않는다.** 사용자가 이유와 함께 고르면 "사용자 결정"으로 기록. 추천 전에 「가정 고르기」를 거친다 |
| 120분 점검 | 남은 필수, 버릴 수 있는 선택조건 |
| 검사 실패가 반복될 때 | 원인 가설 2~3개와 확인 방법 |
| 제출 직전 | 미충족·미검증 목록, 남은 시간에 할 것 하나 |

- **업무 기준인지 설계 선택인지**: 결과(금액·한도·오류 코드·포함/제외·순서·날짜 경계)가 달라져 담당자가 신경 쓸 것이면 업무 기준 → 담당자 질문부터. 담당자가 몰라도 되는 구현 방법(저장 방식·구조·라이브러리)만 사용자 A/B.
- 선택지는 짧게. 긴 설명은 사용자가 물을 때만.
- 사용자가 "알아서"라고 하면 추천안으로 진행하되, 그 사실을 기록한다.

## 가정 고르기 (담당자가 "기준 없음"이라고 했을 때)
- **영향 크기부터 표시한다.** 출력 필드의 값·채우는 시점·기본값처럼 **모든 결과 행에 찍히는 것**은 "영향 큼"이다. 한 번 틀리면 거의 모든 검사가 함께 틀린다.
- **README의 간접 단서와 대조한다.** 필드 이름, 선택조건, 화면 설명, 예시 출력이 한쪽을 전제하는지 본다. 예: "담당자별 처리 대기 목록"이 선택조건에 있으면 담당자는 접수 때부터 정해져 있어야 한다.
- **고치라고 받은 초안 코드의 현재 값은 근거로 쓰지 않는다.** 초안은 고칠 대상이다. "초안 초기값 보존"을 추천 이유로 쓰지 않는다.
- 영향 큼인데 단서가 없으면 **다른 담당자에게 한 번** 묻는다. 그래도 없으면 단서가 가리키는 쪽을 추천하고, 문서에 "가정 · 영향 큼 · 틀리면 바꿀 곳"을 남긴다.

## A/B를 고르는 기준

개발 지식의 많고 적음으로 고르지 않는다. 아래를 **위에서부터** 비교하고, 먼저 차이가 나는 항목에서 더 나은 안을 고른다.

1. 담당자의 명시적 요구를 더 직접 만족하는가?
2. 실패해도 기존 데이터나 확정 결과가 보존되는가?
3. 정상·경계·실패 사례로 실제 검사할 수 있는가?
4. 더 단순하게 설명하고 구현할 수 있는가?

그래도 같으면 **변경 범위가 작고 되돌리기 쉬운 안**을 고른다. 필요한 업무 기준이 비어 있으면 이 순서로 억지 선택하지 말고 담당자 질문 한 문장으로 돌린다.

## 다른 세션에 A/B 선택을 맡길 때 (선택 · 읽기 전용)

작업 세션은 사용자가 내용을 다시 설명하지 않도록 먼저 아래 **선택 카드**를 채운다. 다른 세션은 대화 맥락을 자동으로 모르므로 카드 없이 `A/B 중 골라 줘`만 보내지 않는다.

```text
[A/B 선택 카드]
결정할 것:
확정 요구·출처:
A: 내용 / 실패 시 기존 결과 / 검사 방법 / 변경 범위
B: 내용 / 실패 시 기존 결과 / 검사 방법 / 변경 범위
작업 세션의 추천과 이유:
아직 비어 있는 업무 기준:
```

다른 세션에는 카드와 함께 이것만 보낸다.

```text
kit/playbooks/decision-gates.md 기준으로 아래 A/B 중 하나를 골라 줘. 코드는 고치지 마.
```

검토 세션은 **요구 직접성 → 기존 결과 보존 → 검사 가능성 → 단순성** 순서로(보존 대상은 제공 자료·확정 결과다. 고치라고 받은 초안 코드의 값은 보존 근거가 아니다) 판단하고 아래 형식으로만 답한다.

```text
선택: A 또는 B
이유: 요구 / 보존 / 검사 / 단순성
가장 큰 위험:
작업 세션에 보낼 말: "선택은 __. 이유는 __이며, __로 확인해 줘."
```

- 카드에 필요한 업무 기준이 비어 있으면 선택하지 않고 `담당자에게 보낼 질문 한 문장`을 준다.
- 검토 세션은 파일 수정·명령 실행·커밋을 하지 않는다. 구현과 최종 검사는 작업 세션만 한다.
- 작업 세션은 돌아온 답을 맹목적으로 따르지 않고 확정 요구와 검사 방법이 맞는지 확인한 뒤, 최종 선택과 이유를 기록한다.
- 검토로 추천이 바뀌면 `처음 제안 → 다시 생각한 근거 → 최종 선택 → 확인 방법`을 남긴다. 확인 문제의 AI 제안 수용·수정·폐기 답으로 쓸 수 있다.
