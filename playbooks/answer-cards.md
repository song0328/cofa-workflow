# 확인 문제 답 카드 — 9가지 질문 축과 답 틀

확인 문제는 **제출물(코드·README 요구 문서·검사 파일)과 작업 기록을 AI가 읽고 사람마다 다르게** 만든다. 10/31 관찰에서는 6문항·문항당 약 5분·코드를 볼 수 없는 형식이었다. **실제 화면이 우선**이다.

10/31 응시자 기록을 겹치면 문항은 **6칸**(방법 선택 · 구조·데이터 흐름 · 구현 vs 가정 · 장애·운영 · 변화·판단 · AI 협업 사례)으로 거의 같았다(`playbooks/followup-prep.md` 「예상 칸 6개」). 아래 9개 카드는 그 칸을 더 잘게 나눈 것이다. 내 파일로 예상 질문을 뽑으려면 `tools/predict_questions.py`.

이 파일은 **작업 전·중에 사람이 읽는 답 틀**이다. AI는 이 틀에 실제 값을 채워 `<키트>/notes/확인문제-노트.md`에 남긴다(`playbooks/followup-prep.md`).

## 모든 답의 뼈대 — 4단계
**① 결정과 이유 → ② 약점 → ③ 파급 → ④ 다음 검증**

- ① 무엇을 왜 택했나. 목적·제약·규모의 말로 쓴다. 예: "정원 위반 0이 hard 조건이라 …"
- ② 그 선택의 구체적 약점. 파일·함수·숫자로 짚는다.
- ③ 그 약점이 누구에게 무엇을 깨뜨리나.
- ④ 다음에 무엇으로 확인하거나 개선하나. 명령·테스트·지표로 쓴다.

①만 쓴 답은 절반이다(다른 응시자의 10/31 복기). 5분이 모자라면 ①·②·④만 한 문장씩 쓴다.

## 5분 쓰는 법
1. 0:30 동안 질문을 쪼갠다. 한 문항이 여러 가지를 묻는다(방식·이유·대안·한계).
2. 1:00까지 **이름표부터 친다**: `방식: / 이유: / 대안과 차이: / 포기한 것: / 확인:`
3. 4:30까지 이름표마다 한두 문장을 채운다. 실제 값 하나(숫자·입력·오류 코드)를 꼭 넣는다.
4. 빈 이름표에는 한 줄이라도 쓴다. 시간이 끝나면 자동 확정된다.

**전제가 틀린 질문**에는 이렇게 시작한다: "질문은 A를 전제로 했지만, 실제 구현은 B 때문에 C로 했습니다." 그다음 본인 작업을 설명한다.
**구현하지 않은 것**을 물으면: "그 기능은 만들지 않았습니다. 이유는 ○○입니다. 넣는다면 지금 구조의 ○○ 단계에 ○○ 방식으로 넣겠습니다."
**세부 코드를 모를 때**: "세부 코드는 AI가 작성했고, 저는 역할과 결과를 확인했습니다. `X`는 ○○를 맡고, ○○를 넣어 ○○ 결과로 확인했습니다."

개발 지식이 없어도 용어를 외우지 않는다. **실제 역할 한 명과 데이터 한 건**을 골라 파일·함수 이름표만 붙여 이동 경로를 설명한다. 모르는 내부 문법보다 `누가 넣음 → 어디서 검사 → 무엇이 바뀜 → 누가 봄`이 우선이다.

## 하지 않는 것
- 모르는 것을 아는 척하지 않는다. 하지 않은 테스트를 "테스트했다"고 쓰지 않는다. 코드와 어긋나는 유창한 답이 가장 나쁘다.
- AI 탓·시간 탓을 하지 않는다. "시간이 없어 못 했다" 대신 "○○를 우선해 ○○는 뺐고, 그 위험은 ○○다".
- "어느 파일을 보면 나온다"로 답을 대신하지 않는다. 내용을 내 말로 쓴다.
- 남의 키트·예시 문장의 숫자를 외워 쓰지 않는다. 내 결과의 숫자만 쓴다.

## 카드 1. 방법·알고리즘 선택
나오는 모양: "단순한 방법 대신 왜 이 방법을 썼나 / 왜 (최적화) 알고리즘을 짜지 않았나 / 왜 더 강한 방법(정확해·실시간)이 아닌가 / 휴리스틱을 쓴 이유와 한계"
- ① 목적 한 줄과 hard 조건 → 고른 방법(A 단순 / B 휴리스틱+개선 / C 정확해 중 무엇) → 고른 이유(시간·설명 가능성·데이터 규모)
- ② 전역 최적을 보장하지 않는다. 하한 대비 격차가 n%다.
- ③ 특정 입력(쏠림·이상값)에서 품질이 나빠질 수 있다.
- ④ 기준선 대비 개선 수치 → 다음 개선안(지역 탐색·정확해 비교)
- 미리 채울 값: **기준선 vs 개선안 지표표 한 줄**, 계산 시간, 하한
- 근거: `playbooks/types/optimization.md`

## 카드 2. 구조·데이터 흐름
나오는 모양: "각 모듈의 책임과 데이터 흐름 / 상태는 어디에 저장되고 누가 바꾸나 / 운영자가 입력한 것이 어떻게 저장돼 사용자 화면에 뜨나"
- 흐름 한 줄: `역할의 입력·클릭 → 검증 → 계산 → 확정·저장 → 조회 → 다음 역할의 화면` + 단계마다 실제 파일·함수
- 구조 표: `파일·함수 / 들어오는 값 / 책임 / 내보내는 값 / 저장 상태와 소유자`. "프론트·백엔드"만 말하지 말고 경계를 실제 이름으로 짚는다.
- 역할별 표: `사용자·운영자·담당자(실제 있는 역할만) / 볼 것 / 바꿀 것 / 어디서 권한·규칙을 검사 / 바뀐 뒤 누가 봄`.
- 대표 데이터 한 건을 끝까지 추적한다. 담당자가 앱 사용자가 아니라 규칙 제공자라면 `담당자 답 → 확정 규칙 → 계산·검사 → 사용자 결과`로 설명한다.
- 실패 경로도 한 줄: 어느 단계에서 거절되고 기존 저장 상태와 화면 메시지는 어떻게 되는가.
- 근거: README의 구조 표, `knowledge/service-architecture.md`

## 카드 3. 권한·데이터 격리

### PRD·SSOT·구현 계획을 쓴 경우
- 답 순서: **PRD 근거(README·담당자 답) → 보안 SSOT 권한표 → 실제 강제 파일·함수/API → 권한 밖 거절 검사 → 한계·운영 첫 일**.
- `PRD`, `SSOT`라는 이름만 말하지 않는다. 내 제출물의 실제 절·표 이름, 그 표 때문에 바뀐 코드, 직접 본 실패 결과를 연결한다.
- 정상 로그인만 보여 주지 말고 `인증 없음`, `A로 로그인해 B의 ID 요청`, `이용자로 운영자 API`, `비밀번호·해시가 응답·로그에 없음` 중 구현 범위의 거절 근거를 하나 이상 말한다.
- 정적 화면뿐이면 **화면 구분은 구현했지만 실제 인증·데이터 격리는 아니다**라고 먼저 선을 긋고, 운영 전 서버 인증·서버 측 필터를 넣을 위치를 말한다.
- 예상 꼬리 질문:
  - 왜 이 인증 방식을 골랐고 더 강한 방식은 왜 뺐나?
  - SSOT의 한 행이 바뀌면 어느 API·화면·검사를 같이 고치나?
  - 버튼을 숨긴 것과 서버에서 막은 것은 어떻게 다른가?
  - 사용자 ID나 `role=admin`을 요청에서 바꾸면 왜 권한이 바뀌지 않나?
  - 비밀번호 원문은 어디에도 남지 않는가? 직접 무엇으로 확인했나?
나오는 모양: "운영자/사용자 데이터를 어떻게 격리했나, 각각 무슨 권한이 있나"
- 역할별 표: 볼 수 있는 것 / 바꿀 수 있는 것
- **어디서 막나**: 서버에서 세션의 사용자 ID로 확인한다. 클라이언트가 보낸 ID는 믿지 않는다. 응답에서 다른 사람의 필드를 뺀다. 화면에서 버튼을 숨기는 것은 보조일 뿐이다.
- 확인: "A로 로그인해 B의 데이터 요청 → 403/404"를 실제로 돌렸나
- 약점 예: 세션이 메모리에 있어 재시작하면 로그아웃된다. 운영 전에는 DB 세션·만료·HTTPS가 필요하다.
- 근거: `knowledge/security.md`

## 카드 4. 장애·동시 수정·오류
나오는 모양: "어떤 장애가 생기면 코드상 어떻게 되나 / 다른 운영자가 동시에 수정하면 / 계산 중 오류가 나면 / 같은 요청이 반복되면 / 데이터가 틀리면 누가 책임지나"
- 이미 구현한 것과 운영 전에 할 것을 **나눠서** 쓴다. 하지 않은 것을 했다고 하지 않는다.
- 틀:
  1. 실패하면 이전 확정본을 유지한다(트랜잭션 / 임시 파일 → 교체).
  2. 동시 수정은 버전을 비교한다. 다르면 409 "다른 사람이 먼저 바꿨다".
  3. 계산 중에는 다시 실행을 막는다.
  4. 변경 기록(누가·언제·무엇)을 남긴다.
  5. 되돌릴 수 있게 한다.
- 확인: 깨진 입력을 넣었을 때 이전 결과가 그대로인지 직접 봤나
- **"데이터가 틀리면 누가 발견·수정·승인·복구하나요?"** — 한 사람을 지목하지 않는다. 답 틀: **오류 위치 → 책임 분리 → 보존·복구 → 한계**.
  - 30초 답 틀: "원천 자료의 정확성은 ○○(업무 데이터 소유자)가, 입력 차단과 오류 기록은 서비스가, 복구·재처리는 ○○(운영자)가 맡습니다. 확정 결과를 바꾸는 승인은 ○○(업무 결정권자)가 합니다. 틀린 행은 조용히 고치지 않고 원문·사유를 남겨 격리하고, 실패하면 마지막 확정본을 유지합니다. AI는 제안과 검사를 보조할 뿐 승인·책임 주체가 아닙니다."
  - ○○에는 README·담당자 답의 실제 역할을 넣고, 정해진 게 없으면 "내 가정"이라고 말한다. 내 구현에서 격리 목록·확정본 유지를 실제로 확인한 입력 하나를 붙인다.
- 근거: `knowledge/service-architecture.md`, `knowledge/data-quality.md` 「소유권과 오류 대응」

## 카드 5. 아키텍처·기술 선택
나오는 모양: "무엇으로 만들었나(HTML/React 등) / 모놀리스 vs 분리 / 동기 vs 비동기 / 운영(프로덕션) 전제라면"
- 지금: 스택 한 줄. 왜: 3시간·의존성 없이 바로 띄울 수 있음·화면 수가 적음.
- 설계 판단 5문:
  1. 어떤 요구 때문에 이 구조인가
  2. 더 단순한 대안은 언제 충분한가
  3. 지금 선택이 유효한 규모·조건
  4. 무엇이 바뀌면 다시 검토하나
  5. 이유가 실제 코드와 맞나
- 운영 전제라면: 계산을 작업(job)으로 분리 + 상태 조회, DB(동시성), 인증 강화, 로그·헬스체크·백업. 지금 한 것과 나눠 쓴다.
- **과잉 설계도 감점이다.** 읽기 위주 기능에 무거운 보호를 넣지 않은 이유를 말할 수 있으면 좋다.

## 카드 6. AI 협업·AI 코드 검증
나오는 모양: "AI가 생성한 코드를 반영할 때 무엇을 가장 중요하게 검증하나, 왜 / AI 제안 중 무엇을 받아들이고·고치고·버렸나 / (문서에 적은) 그 문제를 어떻게 발견했나"
- 특히 잘 나오는 사례를 6칸으로 쓴다: **AI 첫 제안 → 내가 `다시 생각해 봐`라고 한 계기·내 주장 → AI가 다시 비교한 대안 → 내가 고른 결론과 이유 → 바뀐 파일·동작 → 확인한 증거(명령·수치)**.
- 내 주장은 실제 대화에서 내가 말한 것만 쓴다. 단순히 AI가 스스로 고친 일을 "내가 지시했다"고 꾸미지 않는다. 반대로 반영하지 않은 주장도 `왜 유지했는지`를 말하면 좋은 판단 사례다.
- 꼬리 질문 대비: "처음 제안을 그대로 썼으면 누구에게 어떤 문제가 생겼나?", "무슨 증거가 나오면 반대 결정을 했나?"
- 일반 답: 요구·제약 충족(hard 조건 위반 0), 경계값, 실패 시 상태 보존, 권한, 숫자는 독립 재계산. "AI가 만든 테스트 통과"는 AI 해석대로 돈다는 뜻일 뿐이라 원자료로 기대값을 따로 만든다.
- 근거: README 요구 문서 안에 작업 중 남긴 AI 협업 판단

## 카드 7. 검증·구현과 가정·한계
나오는 모양: "실제로 구현한 것과 확인 방법 / 구현·검증한 것과 가정의 구분 / 확인하지 못한 것"
- 구현+검증 / 구현했지만 미검증 / 가정 / 안 함 — 네 칸으로 나눈다.
- 확인 수단: 제공 검사 n개, 내가 만든 검사 m개, 화면에서 직접 본 입력 3개(정상·경계·오류)
- 한계 하나 → 생길 문제 → 다음에 할 일

## 카드 8. 트레이드오프·규모·조건 변화
나오는 모양: "트레이드오프는 / 데이터가 10배면 어디가 먼저 무너지나 / 조건이 바뀌면 무엇을 고치고 무엇을 다시 검증하나 / 같은 입력에 같은 결과인가, 동점은"
- 트레이드오프 2쌍을 숫자로: "A로 X가 n% 줄었지만 Y가 m만큼 늘었다"
- 10배: 계산 시간(O(n²) 거리표 등), 메모리, DB 쓰기, 화면 목록. 먼저 무너지는 곳 하나와 대책
- 조건 변경: 바꿀 설정 위치(코드 상수가 아니라 설정) → 다시 돌릴 검사
- 결정론: 정렬 키·동점 규칙·고정 시드

## 카드 9. 요구사항·담당자·예외·범위
나오는 모양: "담당자에게 무엇을 왜 물었나 / 어떤 예외를 어떻게 찾았나 / 자료끼리 다르면 / 무엇을 뺐나"
- 예외를 찾은 방법: 진단 도구로 후보 n개 → 영향 큰 순서로 근거를 붙여 질문 → 답이 바꾼 것 → 그 예외를 지키는 테스트 이름
- 파일에 없던 규칙 → 물은 질문 → 답이 바꾼 것(실제 값)
- 기준 없음 → 내 가정과 이유(사용자 결정)
- 뺀 것과 이유(시간·위험), 그 위험

## 미리 문장으로 써 둘 3개 (작업 중 AI가 노트 맨 위에 채운다)
1. **상충 조건 한 문장**: "반드시 지킬 조건(○○)과 점수로 조정한 조건(○○)을 섞지 않았다. 이유는 ○○."
2. **가장 위험한 실패 입력 하나**: 무엇을 넣으면 무엇이 틀어지나, 지금은 어떻게 막았나
3. **AI를 믿지 않은 곳 하나**: 무엇을 보고 고쳤나
