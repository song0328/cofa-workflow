# 예외 탐색 — 자료에서 숨은 조건을 찾아 담당자 질문으로 바꾼다

좋은 모델은 적힌 요구사항은 대부분 채운다. 점수를 가르는 것은 **적히지 않은 조건**을 찾았느냐다. 예: 특정 요일에 일부만 쉬는 날, 자정을 넘는 근무의 날짜 귀속, 다른 파일에 없는 사람, 자원 상한. 담당자는 이런 것을 먼저 말해 주지 않는다. **근거를 들고 물으면** 답한다.

언제: ① 분석의 첫 15분, 그리고 새 자료·변경본·공지를 받았을 때. 결과는 요건표·질문 목록·테스트가 된다.

## 1. 기계로 먼저 훑는다 (명령 1회)
```bash
python3 <키트>/tools/data_profile.py <자료 폴더>          # 파일별 진단 + 파일 간 키 대조
python3 <키트>/tools/data_profile.py --compare <원본> <변경본> --key <열1,열2>   # 두 판의 차이
```
- 출력 내용: 인코딩, 열 형식, 빈칸, 고유값, 범위, 요일 분포, 대소문자만 다른 값, 시작 > 종료(자정 넘김?), 24시 이상 표기, 키 중복, 파일끼리 맞지 않는 키.
- 개인정보로 보이는 열은 값을 찍지 않는다.
- 과제에 "오류 검증용", "변경본", "changed" 같은 자료가 있으면 **반드시 `--compare`**를 돌린다. 무엇이 깨졌는지 알아야 "거절할 오류"인지 "반영할 갱신"인지 물을 수 있다.
- 그다음 각 파일을 `head -5`로 실제 몇 줄 본다. README의 단어와 실제 열 이름·값을 대조한다.

## 2. 사람 눈으로 볼 9가지 (도구가 못 보는 것)
| 눈 | 찾을 것 | 질문 예 |
|---|---|---|
| 시간 경계 | 자정 넘김의 날짜 귀속, 특정 요일·날짜에 분포가 튐, 공휴일·특별한 날 | "밤 10시에 시작해 다음날 6시에 끝나는 근무는 시작일 계획에 넣나요?" |
| 상태 값 | 문서에 없는 상태, 표기 변형(WORK/work), 일부만 해당하는 특별한 날 | "특정 날짜에 근무자가 크게 줄었는데, 그날은 전원 휴무인가요, 사람마다 다른가요?" |
| 누락 | 다른 파일에 없는 키, 빈칸의 뜻(0인가, 미측정인가, 오류인가) | "근무표에는 있는데 직원 목록에 없는 3명은 제외하나요, 오류로 거절하나요?" |
| 중복·정정 | 같은 대상의 여러 행, 정정·취소 기록 | "같은 사람의 같은 날 행이 두 개면 어느 쪽이 맞나요?" |
| 범위·이상값 | 음수, 0, 좌표가 영역 밖, 너무 큰 값 | "이동시간이 0인 구간 n건은 같은 지점인가요, 자료 오류인가요?" |
| 용량·상한 | 총수요 vs 자원 상한(하한 계산), 한 번에 처리할 최대량 | "쓸 수 있는 ○○ 수에 상한이 있나요?" |
| 문서 vs 자료 | README 설명과 다른 열·값, 언어별 README의 차이, 예시와 실제의 차이 | "README에는 A라고 되어 있는데 자료에는 B가 있습니다. 어느 쪽이 맞나요?" |
| 사용 상황 | 누가·얼마나 자주·동시에 쓰나, 실패하면 어떻게 되나 | "계산이 실패하면 기존 결과를 계속 써도 되나요?" |
| **당사자 선호** | 제한·금지 규칙의 **반대편**: 그 제한을 받는 사람들이 가장 원하는 시간·방식. 공지·게시판·민원의 건의는 거절 대상이기 전에 선호의 단서다. 금지와 선호가 부딪히는 곳이 숨은 기준이다 | "○○ 근무자는 언제·어떻게 받는(쓰는) 게 가장 편한가요?" · "게시판 건의 중 받아들일 수 있는 부분이 있나요?" |

## 3. 예외 후보 표 (AGENTS.md 「3. 가정」 위나 분석 답에)
| # | 후보 | 근거(파일·열·건수) | 결과에 주는 영향 | 담당자 질문 | 답 전 처리 |
|---|---|---|---|---|---|
| E1 | | `schedule.csv` `shift_end` < `shift_start` 1건 | 날짜별 배정이 하루 어긋남 | "…?" | 보류(구현하지 않음) |
- 영향이 큰 순서로 정렬한다. 사람은 **맨 위 하나만** 보낸다(`playbooks/stakeholder.md`).
- 질문 모양: **근거 + 선택지 하나의 문장**: `"[파일]의 [열]에 [값]이 n건 있는데, ○○로 봐도 될까요, △△로 봐야 할까요?"`
- 답을 받기 전에 그 부분을 구현해야 하면 추측하지 않는다. **거절 또는 보류 + 기록**으로 두고 가정에 적는다. 조용히 0이나 휴무로 바꾸지 않는다.

## 4. 답을 받으면
1. AGENTS.md 「2-1. 받은 자료」에 원문을 적고 확정 사양에 반영한다.
2. **예외 하나 = 테스트 하나.** 이름에 내용을 쓴다(`test_overnight_shift_counts_on_start_date`). 함정 입력(예외를 지킨 것 vs 어긴 것)의 결과가 달라야 한다.
3. `DECISIONS.md` 「3. 확정 사양과 가정」에 출처와 함께 한 줄 적는다.
4. 확인문제 노트 카드 9(담당자)와 카드 4(오류 처리)에 실제 값을 넣는다.

## 5. 서술형 재료
- "어떤 예외를 어떻게 찾았나": 진단 도구로 n개 후보 → 영향 큰 순서로 담당자 확인 → 답이 바꾼 것 → 테스트 이름
- "AI 제안을 고친 곳": 예외를 AI가 조용히 가정했다면 그 사례를 `AI_COLLABORATION.md`에 적는다(예: 빈칸을 0으로 처리 → 담당자 확인 후 거절로)
- 찾았지만 답을 못 받은 것은 카드 7(가정·한계)에 적는다
