# 확인 문제 대비 — 작업하면서 미리 준비한다

제출 뒤 확인 문제는 **고정된 제출물을 바탕으로** 나오고, **본인의 작업을 설명하는 답변**이 평가된다. 줄 번호 암기보다 **내가 한 결정을 내 말로** 말할 수 있으면 된다. 확인 문제 중에는 키트·AI를 쓸 수 없으므로, **작업 중에** 준비한다.

형식(공개 안내·사전 체험 기준): **6문항 × 문항당 5분**(시작 전 준비 대기 최대 10분 — 답변 타이머 아님), 문제마다 시간이 따로 흐르고 끝나면 자동 확정, 이전 문제로 못 돌아감, 붙여넣기 불가. **질문의 전제가 실제 구현과 다르면 그 차이를 먼저 밝히고 본인 작업을 설명한다**(공식 가이드).

## 나올 수 있는 질문 유형 (★ = 사전 체험에 실제로 나온 모양)
| # | 유형 | 문제 모양 | 답에 넣을 것 |
|---|---|---|---|
| Q1 ★ | 핵심 동작과 확인 | "만든 것이 무엇을 하며, 어떻게 확인했나" | 핵심 기능 1~2개 → 직접 해 본 입력과 결과(정상·경계·오류 중 하나) → 검사 명령 |
| Q2 ★ | AI 제안 확인 | "AI 제안을 어떻게 확인·수정했나" | AI가 제안한 것 → 내가 본 것(출력·파일) → 고치거나 거절한 것과 이유 |

| Q6 | 설계 이유 | "왜 이렇게 만들었나" | 선택 → 이유(요건·담당자 답) → 버린 대안 |

| Q8 | 범위·우선순위 | "무엇을 먼저 했고 무엇을 뺐나" | 필수 우선 → 뺀 선택조건과 이유(시간·위험) |
| Q9 | 변경 대응 | "규칙이 바뀌면 어디를 고치나" | 코드 위치 → 테스트 값 → 문서 |
| Q10 | 위험·보안·개인정보 | "업무상 위험은 무엇이고 어떻게 막았나" | 위험 하나 → 막은 방법 → 확인 |

| Q13 | 외부 도구·자료 | "어떤 도구·자료를 어떻게 썼나" | 쓴 것(AI 모델, 본인 공개 작업 키트, 점검 도구, 업무 도구 화면) → 왜 → 결과물은 직접 만들고 확인했다는 점 |

## 확인문제 노트 — AI가 작업 중에 채운다
- **생성·복구**: 시작·이어하기와 매 요청 시작 때 실제 노트 파일이 있는지 확인한다. 없으면 `templates/answer-notes.md`로 즉시 만든다. `DECISIONS.md`는 제출용 근거 기록이며 요약 노트의 대체물이 아니다. 이미 진행한 과제라면 결정 문서·현재 코드·실제 검사 출력·대화에서 확인되는 사실만 해당 Q에 복구한다. 계획 승인·담당자 답·과거 검사를 새로 만들어 쓰지 않는다.
- **짧은 요청**: `확인문제 대비해 줘`·`노트 정리해 줘`·`노트 보여 줘`만으로도 생성·최신화 후 내용을 보여 준다. 사용자가 노트 경로를 외우거나 별도 준비 명령을 보낼 필요는 없다.
- 위치: **`<키트>/notes/확인문제-노트.md`** (시험: `/tmp/kit/notes/…` — 제출 폴더 밖). 틀은 `templates/answer-notes.md`. 키트 폴더에 쓸 수 없으면 과제 폴더 밖 `/tmp/확인문제-노트.md`. **과제(제출) 폴더에는 만들지 않는다.**
- **언제**: 단계가 끝날 때, 사용자가 A/B를 고르거나 AI 제안을 고치게 했을 때, 담당자 답이 규칙을 바꿨을 때. 그때 해당 Q 칸만 고친다.
- **얼마나**: Q마다 **최대 3줄**, 파일 전체 **60줄 이하**. 더 중요한 일이 생기면 덧붙이지 말고 **바꿔 쓴다**. 해당 사례가 없는 Q는 비워 둔다(지어내지 않는다).
- **어떻게**: 실제 값과 출처를 쓴다. 사용자 확인이 기록돼 있을 때만 1인칭으로 쓴다. 예: `토요일 하루를 신청하면 NO_WORKDAYS로 거절되는 것을 화면에서 확인했다(인사팀 답: 근무일만 센다).` AI만 실행했으면 `AI 실행: 토요일 신청 → NO_WORKDAYS / 사용자 직접 확인: 미확인`으로 구분한다. 사용자가 실제로 하지 않은 확인·받지 않은 답은 쓰지 않는다.
- Q13·Q14 재료도 그때그때 남긴다: 무엇을 왜 썼나(예: `ui_sim으로 브라우저 없이 화면 동작 확인`), 토큰을 아낀 실제 행동(예: `키트는 목차와 필요한 파일 1~2개만 읽게 함`, `실패가 반복돼 멈추고 오류 문구부터 확인`).
- 맨 위 3줄은 항상 최신으로: **A 만든 것 한 문장 / B 직접 본 입력·결과 2개 / C 정한 것과 이유 2개.** 시간이 없으면 이 3줄만 읽어도 Q1·Q2·Q5 대부분에 답할 수 있다.
- 실제로 파일을 쓰고 다시 읽어 존재·갱신·60줄 이하를 확인한 뒤에만 `노트 갱신: Q번호`라고 알린다. 파일 쓰기에 실패하면 오류를 밝히며 저장됐다고 말하지 않는다.
- 사용자가 `노트 보여 줘`라고 하면 파일의 최신 상태를 확인·보완한 뒤 내용을 보여 준다. 제출 후 확인 문제가 시작됐으면 이 작업을 중단하고 사용자가 AI·키트 없이 직접 답하게 한다.

## 사용자가 할 것 (3시간 중 5번, 30초씩)
1. 분석 끝: "이게 뭘 만드는 과제야? 한 문장으로" → 따라 읽기 (A)
2. 담당자 답마다: 한 줄로 속으로 요약 (C)
3. A/B 고를 때: 이유를 내 말로 붙여 보낸다 (C)
4. 검사·화면 확인: 결과 하나를 직접 눈으로 본다 (B)
5. 제출 10분 전(또는 일찍 끝나면): `노트 보여 줘` → 두 번 읽고 핵심 단어만 기억

이해가 안 되면 넘기지 말고 "이거 왜 이렇게 했어? 쉽게 두 줄로" — 이해에도 도움이 되고, Q2의 재료가 된다.

## 답 쓰는 요령 (5분, 3~5문장)
1. 첫 문장에 결론 (무엇을 했다 / 무엇으로 확인했다) — 자동 확정되므로 **이것부터 쓴다**
2. 구체적인 입력값·결과를 하나 넣는다 ("빈 이름을 넣으면 400과 오류 문구")
3. 담당자 확인인지 내 가정인지 밝힌다
4. 못 한 것 하나를 솔직히 쓴다
5. 문제에 맞는 노트가 없으면 맨 위 A·B·C 3줄로 조합한다
