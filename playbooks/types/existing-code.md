# 기존 코드 수정 (기능 추가·버그 수정·개선)

**먼저 볼 것 (수정 전)**
1. 실행·테스트 명령을 찾아 **수정 전에 한 번 실행**해 현재 상태를 기록한다(처음부터 실패하는 테스트가 있는지).
2. 바꿀 기능이 지나는 파일만 추린다(`grep -rn`). 전체를 읽지 않는다.
3. 기존 코드 스타일·구조를 따른다. 대규모 리팩터링 금지.

**담당자에게 물을 숨은 규칙 예**
- 기존 동작 중 바뀌면 안 되는 것
- 버그의 "올바른 결과"가 정확히 무엇인가 (재현 입력과 기대값)
- 기존 데이터·사용자에게 영향(마이그레이션 필요 여부)

**흔한 함정**: 고치다가 다른 기능을 깨뜨림, 원인 대신 증상만 막음, 처음부터 실패하던 테스트를 내 탓/내 공으로 착각, 요청 밖 "김에 정리".

**버그 수정 순서**: 재현 입력 확보 → 실패하는 테스트 먼저 작성 → 원인 위치 → 최소 수정 → 그 테스트 + 기존 테스트 전체 통과.

**검증**: 수정 전후 테스트 결과 비교(`git diff`로 바뀐 파일만), 재현 입력이 이제 기대값을 내는지.

**결과물 모양**: 원인 한 줄, 바꾼 파일·이유, 회귀 확인 결과, 손대지 않은 것.
